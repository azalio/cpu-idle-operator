# Финальная верификация — REVISE  Проверялось целое, а не зелёная последняя подзадача. Два блокирующих дефекта живут **в швах между подзадачами**, где каждая сторона по отдельности выглядит правильной.  ## Блокирующее  ### 1. Вес не восстанавливается при снятии idle через путь Apply  Реконсайлер направляет под в `Apply`, если запрошен **любой** тир, и в `Revert` — только когда не запрошено ничего. Но `cpu.weight` пишет исключительно `Revert`.  Сценарий: под несёт обе аннотации (это ровно поставляемый пример `config/samples/pod-both.yaml`), снимают только `tier`. Burst остаётся запрошенным → под идёт через `Apply` → план содержит `[cpu.idle=0]` и ни одной записи веса. Ядро при этом переходе сбрасывает вес в 100 — измеренный факт, на котором стоит весь дизайн. Никто его больше не восстановит: последующий `Revert` тоже пропустит вес, потому что `revertPlan` вставляет его только при `state.IdleActive`, а idle уже снят. `--revert-all` идёт тем же путём.  Итог: под навсегда получает впятеро большую долю CPU, молча.  Воспроизведено моей пробой: `cpu.weight = "1", want "20"`.  Нарушает AC-2 и прямо противоречит фразе README про то, что ни один тир не увеличивает долю пода за счёт соседа.  ### 2. События AC-4 и AC-16 не срабатывают в продакшене  Ранний возврат реконсайлера при пустом плане (добавлен ради INV-6) отрабатывает **до** вызова `Apply`. А `reportNotes`, который шлёт `TierInactive` для burst без лимита и `TierValueUnknown` для незнакомого значения, живёт внутри `Apply`.  Под с `burst` и без `limits.cpu`: `BurstActive=false`, целевой burst 0, фактический уже 0, план пуст → `Apply` не вызывается → ни события, ни метрики. Под с `tier: bogus` — то же самое.  Спека говорит прямо: «Молчать нельзя». Смысл AC-16 в том, что два молчания различимы; в продакшене они схлопываются в одно. Покрытие есть только на юнит-уровне, ни один тест не проходит через реконсайлер.  ## Не блокирующее, но исправляется дёшево  - **README обещает то, чего CI не делает.** Сказано, что `hack/check-readme-keys.sh` роняет CI при расхождении ключей, но в `ci.yaml` подключён только `check-manifests.sh`. # Code review 009 — ST-013 (kind e2e и CI), provisional  ## Open Question №1 закрыт измерением  Вопрос стоял так: видит ли агент внутри kind-ноды тот же cgroup-путь, что kubelet этой ноды. Ответ получен вживую, а не рассуждением.  **Не видит.** kind v0.29.0 задаёт kubelet'у `cgroupRoot=/kubelet`, поэтому поды лежат под `kubelet.slice/kubelet-kubepods…`, а не в голом `kubepods.slice`, который агент выводит из `--cgroup-root=/sys/fs/cgroup`.  Подтверждено двумя независимыми способами: 1. прямое сравнение путей через exec в контейнер-ноду; 2. развёрнутый настоящий DaemonSet из `config/base` — агент **сам** сообщил `Ready=false Reason=kubepods_missing`, `/readyz` отдал 503, `/healthz` 200, и при живом аннотированном поде не сделал ни одной записи в cgroup.  Это не проблема видимости bind-mount: расхождение видно прямо в контейнере-ноде, без всякой прослойки из пода и hostPath. Поэтому `extraMounts` в `kind-config.yaml` сознательно **не** добавлены — рекомендация из исследования оказалась не про эту причину.  ## Что это дало помимо ответа  Побочный результат ценнее самого гейта: поведение из AC-6 и INV-5 проверено **на живом кластере**, а не на фикстуре. Агент на неподдерживаемой ноде остался живым, не ушёл в перезапуск, отдал 503 с причиной и не тронул ни одного cgroup-файла.  ## Что сделано по заранее согласованному запасному пути  - `preflight_test.go` падает с явным текстом, называющим Open Question 1, при расхождении путей. - `e2e_test.go` разворачивает настоящий DaemonSet и ветвится: полный сценарий применения и снятия из AC-10 написан, компилируется и проверен `vet`, но сейчас спит; вместо него проверяется fail-safe поведение end-to-end — и это блокирует merge. - Позитивный сценарий AC-10 остаётся закрыт `hack/stand-probe.sh` на настоящей ноде. - CI: `go vet`, линтер, unit, `hack/check-manifests.sh` и e2e блокируют merge; отдельный шаг явно проверяет cgroup v2 на раннере. Задокументированный отказ pre-flight по Open Question 1 не блокирует, любой другой исход pre-flight — блокирует.  ## Хвост, который стоит проверить отдельно  У агента уже есть флаг `--cgroup-root`. Если указать ему `/sys/fs/cgroup/kubelet.slice`, `kubepods.slice` окажется на месте, и kind-гейт может заработать без правок кода. Это не проверено и вне скоупа ST-013, но выглядит дешевле, чем одноузловая нода в CI.  ## Ограничение прогона  Скомпилированный e2e-бинарь не исполнялся локально: `internal/cgroup` только под Linux, хост — macOS на arm64. Компенсировано ручной проверкой всех операций против настоящего kind-кластера плюс чистой кросс-компиляцией `build` и `vet` под Linux.
