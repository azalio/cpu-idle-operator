# Spec: cpu-idle-operator v1alpha1 — node-agent для cgroup v2 CPU-тиров

Источники решений — два замороженных wayfind-handoff:
`.map/wayfind/cpu-idle-operator/handoff.md` (12 решений) и `.map/wayfind/cpu-idle-tiers/handoff.md` (1 решение, уточняет кодирование тиров).

Цель: публичный репозиторий к докладу про `cpu.idle` (CFP ~октябрь 2026), качество эксплуатационное, не демо.

## Decisions Made

| # | Вопрос | Решение | Обоснование |
|---|---|---|---|
| 1 | Чем объявляется тир | Аннотации на поде, без CRD | idle — самоограничение, эскалации привилегий не даёт; webhook в критическом пути создания подов не окупается |
| 2 | Кодирование тиров | Два независимых ключа: `cpu.azalio.net/tier: idle` и `cpu.azalio.net/burst`. Под может нести оба | Измерено: `cpu.idle` и `cpu.max.burst` живут в разных подсистемах и не конфликтуют |
| 3 | Кто вправе выставлять | Любой владелец пода, без проверки | Навредить соседу тиром нельзя, только себе |
| 4 | Состав компонентов | Один бинарь, один DaemonSet. Ни контроллера, ни CRD, ни webhook, ни leader election | Без CRD контроллеру нечего реконсайлить |
| 5 | Фреймворк | controller-runtime как библиотека, без kubebuilder-скаффолда | Скаффолд нужен под CRD и webhook, которых нет |
| 6 | Определение pod-cgroup | Вычисление из pod UID и QoS-класса через `github.com/opencontainers/cgroups` | Проверено на стенде: формула совпала точно. Walk по дереву хрупок и медленен |
| 7 | Восстановление веса | Агент пересчитывает из `requests.cpu` по формуле kubelet, строго после `cpu.idle=0` | Измерено: ядро оставляет вес 100 вместо request-derived 20, kubelet живой pod-cgroup не трогает |
| 8 | Поведение при остановке | Ничего не откатывать. Осознанный откат — отдельный режим `--revert-all` | Откат на SIGTERM превращал бы rolling update в инцидент по p99 прода и не сработал бы при SIGKILL |
| 9 | Supported окружения | cgroup v2 unified, ядро 5.15+, драйвер systemd. cgroupfs реализован, но experimental | v1 не содержит `cpu.idle`. cgroupfs-ноды для проверки нет |
| 10 | Реконсиляция | Событийный informer по подам своей ноды + resync 60 с как страховка | За 120 с наблюдения дрейфа не было; тесный цикл 2 с не окупается |
| 11 | Тестирование | unit + kind e2e гейтят merge; четыре ядерных факта — в `hack/stand-probe.sh` | Рестарт kubelet и EINVAL невоспроизводимы без настоящего ядра |
| 12 | Дифференциатор | Пишем только на pod-cgroup, никогда на QoS-слайс | Koordinator и upstream PR пишут на слайс и упираются в EINVAL-коллизию upstream issue 136025 |
| 13 | Метрики | Только bounded-лейблы: `node`, `namespace`, `qos_class`, `result`, `reason` | `pod_name` у Deployment-подов меняется при каждом рестарте — тот же cardinality-взрыв, что и `pod_uid` |
| 14 | Источник QoS-класса | Вычисляем сами чистой функцией от `spec` по формуле kubelet. `status.qosClass` читаем только как сверку и логируем расхождение | Путь pod-cgroup зависит от класса. Поле статуса заполняется не нами и на свежесозданном поде может ещё отсутствовать — это гонка на самом горячем пути. Вычисление из `spec` детерминировано и доступно сразу |

Принятые самостоятельно, легко обратимы (см. Open Questions): Go module `github.com/azalio/cpi-idle-operator`, CI — GitHub Actions, лицензия Apache-2.0.

## Contradiction

Оператор пишет в файлы, которыми по праву владеет kubelet, и обязан при этом никогда с ним не столкнуться.

Разрешение держится на одном измеренном факте: kubelet конфигурирует pod-cgroup ровно один раз при создании и больше в него не возвращается, тогда как QoS-слайс переписывает каждые 60 секунд и на каждое событие пода. Весь дизайн — следствие этой асимметрии. Любая запись выше pod-cgroup немедленно ломает контракт и втаскивает нас в чужую коллизию.

Вторая грань того же напряжения: ядро вводит инварианты между соседними knob'ами (`cpu.idle` запирает `cpu.weight`, `cpu.max.burst` запирает понижение квоты), а Kubernetes про них не знает. Оператор обязан соблюдать порядок операций, который нигде в API не выражен.

## Invariants

- **INV-1.** Агент пишет исключительно в pod-cgroup. QoS-слайсы, корневая cgroup и container-level scope'ы — только чтение, и то лишь при диагностике.
- **INV-2.** `cpu.weight` не записывается никогда, пока `cpu.idle=1`. При снятии тира порядок строго: сначала `cpu.idle=0`, затем вес.
- **INV-3.** Любая запись в cgroup-файл проверяет ошибку на закрытии дескриптора, а не только на самой записи. Ошибка, потерянная в буфере, означает молча непринятую политику.
- **INV-4.** Остановка агента любым способом не изменяет ни одного значения cgroup. Единственное исключение — явно запрошенный режим `--revert-all`.
- **INV-5.** На ноде, не прошедшей environment gate, агент не выполняет ни одной записи.
- **INV-6.** Реконсиляция идемпотентна: повторный проход по неизменившейся ноде не производит записей и не логируется как работа.
- **INV-7.** При одновременной установке обоих тиров ширина полосы записывается раньше порядка выбора: сначала `cpu.max.burst`, затем `cpu.idle`. При снятии — в обратном порядке.

## Constraints

**Hard**

- **HC-1.** Только cgroup v2 unified. Обнаружены v1 или hybrid — агент отказывается работать с явным указанием причины.
- **HC-2.** Минимальная версия ядра 5.15. Ниже — тот же отказ.
- **HC-3.** Никаких обращений к CRI-сокету, к containerd и к `/proc/<pid>/cgroup`. Путь pod-cgroup выводится только из UID пода и его QoS-класса.
- **HC-4.** В v1alpha1 нет CRD, нет admission webhook, нет leader election и нет второго бинаря.
- **HC-5.** Метрики не содержат лейблов неограниченной мощности. `pod_name`, `pod_uid`, `container_id` запрещены.
- **HC-6.** Манифест DaemonSet не требует `privileged: true` и не запрашивает `SYS_ADMIN`. Измерено: достаточно hostPath на запись и uid 0.

**Soft**

- Ветка cgroupfs-драйвера реализуется, но заявляется experimental и сопровождается предупреждением в логе.
- Величина burst по умолчанию равна квоте; переопределение числовым значением аннотации в первой версии не парсится.

## Edge Cases

- Под с `burst`, но без `limits.cpu`: квоты нет, копить нечего. Применяем, вешаем Event о том, что тир неактивен. Молчать нельзя.
- Под несёт оба ключа одновременно: обрабатываются независимо, порядок применения — сначала полоса, затем порядок выбора.
- Аннотация меняется у живого пода: informer обязан ловить update, а не только add.
- `requests.cpu` изменился, пока под в idle: kubelet свою запись веса провести не смог, при снятии тира восстанавливаем новый запрос, а не запомненный при входе.
- Под без `requests.cpu`: восстанавливаемый вес равен 1.
- Пересоздание пода: новый cgroup, значения по умолчанию, агент применяет тир заново.
- Незнакомое значение ключа тира: трактуется как отсутствие тира, Event, не ошибка.
- Понижение лимита ниже выставленного burst: ядро вернёт EINVAL. Агент это фиксирует и сообщает, но не воюет за файл.
- Гонка «под удалён между чтением из informer и записью в cgroup»: каталог исчез — не ошибка, тихо пропускаем.

## Acceptance Criteria

- **AC-1.** Под, созданный с ключом `cpu.azalio.net/tier: idle`, получает `cpu.idle=1` на своём pod-cgroup. Числовой порог задержки не задаётся: он ничем не измерен (см. Open Questions), тест проверяет факт применения с разумным таймаутом ожидания, а не SLA.
- **AC-2.** Снятие ключа `tier` возвращает `cpu.idle=0` и восстанавливает `cpu.weight`, пересчитанный из `requests.cpu` по формуле kubelet, — проверяется на измеренной паре 500m и 20.
- **AC-3.** Под с `cpu.azalio.net/burst` и выставленным `limits.cpu` получает `cpu.max.burst`, равный квоте из `cpu.max`.
- **AC-4.** Под с ключом `burst`, но без `limits.cpu` не приводит к ошибке и получает Event с указанием, что тир неактивен без лимита.
- **AC-5.** После перезапуска агента состояние ноды приводится в соответствие с аннотациями, при этом сама остановка агента не изменила ни одного значения cgroup.
- **AC-6.** На ноде с cgroup v1 агент остаётся not-ready, не перезапускается циклически, экспортирует метрику с причиной и вешает Event на каждый аннотированный под.
- **AC-7.** Запуск с `--revert-all` снимает оба тира со всех подов ноды, восстанавливает веса и завершает процесс с нулевым кодом.
- **AC-8.** Экспортируемые метрики покрывают: число подов в каждом тире, количество применений по результату, счётчик расхождений при resync, причину отказа окружения — и не содержат ни одного запрещённого лейбла.
- **AC-9.** `hack/stand-probe.sh` печатает таблицу «проверка / ожидалось / получилось» по четырём фактам (выживание при рестарте kubelet, выживание цикла UpdateCgroups, EINVAL на записи веса в idle-cgroup, потеря request-derived веса при снятии idle) и возвращает ненулевой код при любом расхождении.
- **AC-10.** E2E-прогон в kind: развёрнутый DaemonSet применяет тир к аннотированному поду и снимает его при удалении аннотации, проверка читает фактические значения из cgroup.
- **AC-11.** README описывает оба тира через рамку Maximum / Yield / Progress, называет матрицу supported окружений и явно предупреждает про исключение обоих тиров из VPA. Критерий проверяется ревью человека, а не автоматическим гейтом: грепом ключевых слов легко пройти с неверным объяснением.
- **AC-12.** Аннотация, добавленная или снятая на **уже живом** поде, применяется и снимается так же, как заданная при создании. Реализация, обрабатывающая только событие добавления пода, обязана этот критерий провалить.
- **AC-13.** Под с обеими аннотациями сразу получает и `cpu.max.burst`, и `cpu.idle`, причём порядок записей соблюдён по INV-7 — порядок проверяется на последовательности вызовов, а не только на конечном состоянии.
- **AC-14.** Под без `requests.cpu` при снятии idle получает восстановленный `cpu.weight`, равный 1.
- **AC-15.** Если `requests.cpu` изменился, пока под находился в idle, при снятии тира восстанавливается **новое** значение, а не запомненное при входе. Реализация, кеширующая вес на входе, обязана этот критерий провалить.
- **AC-16.** Незнакомое значение ключа тира даёт no-op и Event; исчезнувший каталог pod-cgroup (под удалён между чтением из informer и записью) даёт тихий пропуск без ошибки и без Event. Разница между этими двумя видами молчания проверяется явно.

**CCR-1.** Каждое фактическое изменение cgroup сопровождается Event на поде и инкрементом метрики. Изменение без следа запрещено.

## Security Boundaries

Агент монтирует `/sys/fs/cgroup` на запись и работает под uid 0. Это по существу право изменять cgroup любого пода на ноде, и измерение это подтвердило: контейнер с отброшенными capabilities и без privileged успешно записал чужой pod-cgroup. Формулировка «минимальные привилегии» здесь была бы враньём — в README это называется своим именем.

Компенсирующие свойства, а не оправдания: агент не читает и не пишет ничего, кроме `cpu.idle`, `cpu.weight`, `cpu.max`, `cpu.max.burst`; RBAC ограничен чтением подов своей ноды и созданием событий; поверхность API-сервера сведена к одному informer с `fieldSelector`.

Аннотация доступна любому владельцу пода сознательно: оба тира ограничивают того, кто их запросил, и не дают способа получить больше CPU за счёт соседа.

## Out of Scope

- CRD-политика с селекторами и control-plane контроллер — v1beta1.
- Admission webhook и любой гейт прав на аннотацию.
- Поддержка cgroup v1 и hybrid-режима.
- Активное противодействие in-place resize и VPA: конфликт фиксируется и сообщается, но не чинится.
- Числовое переопределение величины burst через значение аннотации.
- Любые заявления об эффекте `cpu.max.burst` на p99 — эффект не измерен.
- Экономия нод и денег как заявляемый результат.

### Already Implemented

Ничего. Репозиторий пуст: кроме `.claude/`, `.map/`, `.gitignore` и `.mcp.json` исходников нет, коммитов в git нет. Discovery-фаза пропущена как бессмысленная на greenfield, и по той же причине пропущен Already-Implemented gate.

## Open Questions

1. **Согласованность cgroup-вида внутри kind-ноды не проверена.** Видит ли агент в контейнере-ноде тот же путь, что kubelet этой ноды. От ответа зависит существование блокирующего e2e-гейта (AC-10). Проверка: поднять kind, создать под, сравнить путь изнутри агента и снаружи. Если не сойдётся — заменить kind на одноузловую ноду в CI и зафиксировать причину. Подзадача, реализующая AC-10, до проверки считается provisional.
2. **Задержка применения тира не измерена ни разу.** В первой редакции спеки в AC-1 стоял порог «пять секунд», взятый с потолка — ревью это поймало, порог убран. Что реально неизвестно: время от появления пода в informer до записи в cgroup, и особенно глубина очереди при массовом создании подов на ноде. Проверка: создать N подов одновременно, снять распределение задержки применения. До замера числовой SLA не заявляется нигде — ни в спеке, ни в README, ни со сцены.
3. Go module path, CI-провайдер и лицензия приняты самостоятельно. Возражения дешевле высказать до первого коммита.
4. Совместимость с одновременно установленным Koordinator — рассуждение, не замер.
5. Минимальная версия Kubernetes заявлена по стабильности схемы имён; прогон был только на 1.36.3.

## Verified Runtime Assumptions

Гейт живого состояния отработан: все факты ниже сняты на стенде 2026-08-16, ядро 6.17, Kubernetes 1.36.3, containerd 2.2.1, драйвер systemd, чистая cgroup v2. Протоколы — в резолюциях wayfind-тикетов про стендовую проверку lifecycle и про burst-тир.

- Формула пути pod-cgroup для systemd-драйвера совпала с вычисленной.
- `requests.cpu` 500m даёт `cpu.weight` 20.
- Запись `cpu.weight` при `cpu.idle=1` возвращает EINVAL для любого значения.
- Переход `cpu.idle` из 1 в 0 оставляет вес 100.
- `cpu.idle=1` пережил два цикла реконсиляции QoS-слайса, создание соседнего пода и рестарт kubelet.
- Запись в cgroup не требует `SYS_ADMIN`.
- `cpu.idle`, `cpu.max` и `cpu.max.burst` сосуществуют на одной cgroup без конфликта.
- `cpu.max.burst` больше квоты и понижение квоты ниже burst возвращают EINVAL.

**Unverified Runtime Assumption:** поведение комбинации обоих тиров на настоящем pod-cgroup под управлением kubelet (рестарт, цикл реконсиляции) не проверялось — ортогональность измерена на голой cgroup. Проверка входит в `hack/stand-probe.sh` (AC-9).
