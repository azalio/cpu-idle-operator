# Code review 004 — ST-006 (internal/tier)

## HIGH — BurstActive вычисляется по неверному правилу

`internal/tier/desired.go`, `hasPositiveCPULimit`: возвращает true, если положительный `limits.cpu` есть **хотя бы у одного** контейнера. Actor пометил это как осознанное сужение со ссылкой на то, что расчёт квоты принадлежит более поздней подзадаче.

Правило kubelet другое, и это **измерено на стенде** 2026-08-17, а не вычитано из исходников:

| Под | `cpu.max` на pod-cgroup |
|---|---|
| два контейнера, у одного нет `limits.cpu` | `max 100000` — квоты нет |
| два контейнера, лимиты 200m и 300m | `50000 100000` — квота равна сумме |

Квота на pod-cgroup появляется, только если `limits.cpu` задан у **всех** контейнеров. Достаточно одного контейнера без лимита, чтобы под остался без квоты.

Следствие: для смешанного пода текущий код вернёт `BurstActive=true`, применитель запишет `cpu.max.burst`, копить будет нечего, и никакой ноты пользователь не получит. Это ровно тот класс «сообщили об успехе, которого нет», из-за которого в этом прогоне уже трижды возвращались правки: незащищённый знаменатель формулы веса, guard-блок-лист, декоративная строка таблицы в стендовом скрипте.

**Требуется:** `BurstActive=true` только когда `limits.cpu` задан и положителен у всех контейнеров пода (по правилам kubelet, с учётом init/sidecar так же, как это сделано в `internal/qos`). Иначе `BurstActive=false` плюс нота `limits_cpu_missing`. Тест обязан покрыть смешанный под — именно он сейчас пробивается.

## Прочее к проверке в той же правке

- Пустое значение ключа tier (`tier: ""`) сейчас не даёт ноты вовсе. Формально контракт говорит про «непустое», но пользователь, написавший пустое значение, что-то имел в виду, и молчание здесь того же класса. Решить явно: либо нота, либо комментарий с обоснованием молчания.

## Итерация 2 — правка внесла тот же дефект в новом месте

Исправление сделало проверку «лимит у всех обычных контейнеров и у всех native sidecar», но **исключило обычные init-контейнеры** с обоснованием, что они не живут одновременно с pod-cgroup в steady state.

Измерено на стенде 2026-08-17:

| Под | `cpu.max` |
|---|---|
| main с `limits.cpu: 200m` + простой init-контейнер **без** лимита | `max 100000` — квоты нет |

kubelet требует лимит и от обычных init-контейнеров: одного init-контейнера без `limits.cpu` достаточно, чтобы под остался без квоты. Рассуждение про steady state здесь не работает — квота задаётся один раз при создании pod-cgroup, а не пересчитывается после завершения init-фазы.

Итого правильное правило: `BurstActive=true` только если положительный `limits.cpu` задан у **всех** контейнеров пода — обычных, native sidecar и простых init.

## Итерация 3 — valid=true, approve

`hasPositiveCPULimit` теперь обходит `Containers` и `InitContainers` без исключений. Мутация (возврат к «хотя бы у одного») валит тест на смешанный под — покрытие настоящее. Мёртвый `isNativeSidecar` удалён, цикла импортов нет.

Два LOW, не блокирующие:
- избыточное перекрёстное утверждение в тесте VC3 — не тавтология, просто мёртвый вес;
- под без контейнеров даёт `BurstActive=true` (пустой цикл истинен). Через API-сервер недостижимо: валидация требует минимум один контейнер. Не покрыто тестом.
