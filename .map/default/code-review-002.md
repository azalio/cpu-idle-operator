# Code review 002 — ST-002 (internal/cgroup)

Monitor итерация 1: valid=false, recommendation=needs_investigation.

## HIGH — guardWriteTarget реализован блок-листом вместо allow-листа (INV-1)

`internal/cgroup/knob.go`, функция `guardWriteTarget`: проверяет, что базовое имя каталога НЕ равно `kubepods.slice`/`kubepods`, НЕ оканчивается на `.scope` и НЕ совпадает с именем QoS-слайса. Всё остальное пропускается.

Monitor подтвердил пробой без мутации кода, простым вызовом функции:
- `guardWriteTarget(t.TempDir())` → `nil`, произвольный каталог принят;
- `guardWriteTarget(".../kubepods-burstable.slice/not-a-pod-at-all")` → `nil`, не-под внутри настоящего QoS-слайса принят.

Три кейса VC3 проходят не потому, что инвариант соблюдён, а потому что случайно совпадают с блок-листом. INV-1 требует обратного: писать разрешено ТОЛЬКО в pod-cgroup.

**Требуемое исправление:** allow-list. Каталог обязан совпадать с тем, что вернул бы `PodCgroupPath` для какого-то валидного сочетания driver/qos/uid. Плюс регрессионные тесты на произвольный каталог и на не-под-подобную поддиректорию внутри QoS-слайса.

## Что Monitor подтвердил как корректное

- VC2 (ошибка Close) — не тавтология: мутация с удалением проверки `closeErr` валит оба теста.
- VC5 (эталон пути) — systemd-ветка совпадает построчно с `hack/stand-probe.sh` и с реальным поведением `ExpandSlice`; ветка Guaranteed без уровня QoS.
- `ErrCgroupGone` переживает обёртки, `errors.Is` работает.
- `errors.Is(err, syscall.EINVAL)` сохраняется сквозь `WriteKnob` — вызывающий код сможет отличить нормальный отказ ядра.
- VC1: литерала `/sys/fs/cgroup` в `internal/cgroup` нет.

## Инцидент с go.mod

Monitor по ошибке запустил `go mod tidy` через раннер `/tmp/gotest-linux.sh`, который смонтирован на РЕАЛЬНЫЙ репозиторий, а не на временную копию. go.mod сократился с ~64 строк до 18, go.sum со 143 до 32.

Решение: не восстанавливать. Удалённые пины — незаимпортированные заглушки из ST-001, которые `go mod tidy` сносит по определению; Monitor ST-001 отметил эту хрупкость как low-риск ещё тогда, и вот она материализовалась. Текущее состояние честнее: в go.mod ровно то, что реально импортируется. Сборка, vet и все тесты под Linux зелёные. Недостающие зависимости вернутся в go.mod вместе с первыми настоящими импортами в ST-005 и ST-009.

Процедурный вывод на остаток прогона: раннер смонтирован на рабочее дерево, поэтому мутационные эксперименты и любые команды, меняющие файлы (`go mod tidy`, `go fmt -w`, генераторы), запускать в нём нельзя — только на копии в /tmp.
