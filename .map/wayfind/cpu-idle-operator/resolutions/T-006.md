# T-006: кто восстанавливает cpu.weight при idle → 0

## Решение

**Восстанавливает агент, пересчитывая вес из `requests.cpu` пода по формуле kubelet. Ждать kubelet бессмысленно — он этот файл на живом поде не пишет вообще.**

Порядок операций жёсткий и обратному не подлежит:

```
1. write cpu.idle = 0      # обязательно первым
2. write cpu.weight = f(requests.cpu)
```

Обратный порядок невозможен физически: запись в `cpu.weight` при `cpu.idle=1` отвергается ядром с EINVAL.

## Почему не kubelet

Измерено на стенде (см. [T-005.md](T-005.md)):

- `cpu.idle: 1 → 0` оставляет `cpu.weight = 100` — kernel default, а не request-derived `20`.
- Per-pod cgroup пережил два цикла `qosContainerManager.UpdateCgroups`, создание соседнего пода и полный restart kubelet — значение никто не поправил.

Это согласуется с чтением исходников в деке: pod-cgroup конфигурируется однократно в `EnsureExists`, всё тело под `if !alreadyExists`. Реконсайлера pod-уровня у kubelet нет. Если агент не восстановит вес, под останется с весом `100` вместо `20` — впятеро больше положенной доли, молча, без единой ошибки в логах. Это худший класс дефекта: тихая деградация справедливости распределения CPU.

## Формула

Та же, что у kubelet для cgroup v2:

```
shares = max(2, milliCPU * 1024 / 1000)
weight = 1 + ((shares - 2) * 9999) / (262142 - 2)      # целочисленно
```

Проверка на измеренном случае: `500m → shares 512 → weight 1 + (510*9999)/262140 = 20`. Совпало с тем, что выставил kubelet.

Граничные случаи:
- **Под без `requests.cpu`** (BestEffort): kubelet даёт минимальные 2 shares, то есть `weight = 1`. Восстанавливаем `1`.
- **Несколько контейнеров**: вес pod-cgroup считается от суммы `requests.cpu` всех контейнеров пода, включая init-контейнеры по правилам эффективного запроса.

## Источник истины — spec, не кэш

Рассматривался вариант «запомнить `cpu.weight` до установки idle и вернуть запомненное». Отклонён как основной:

- кэш теряется при рестарте агента, а idle-поды его переживают — после рестарта восстанавливать будет нечем;
- `requests.cpu` доступен из informer'а всегда и переживает что угодно.

Кэш всё же ведём, но как **детектор расхождений**: если сохранённое до-idle значение не совпадает с пересчитанным из spec, пишем warning и событие на под. Расхождение означает, что вес пода трогал кто-то ещё — то есть работает in-place resize или сторонний агент, и об этом надо знать, а не молча затирать.

## Сцепка с in-place resize и VPA

Измерение подняло это из «рассуждения по исходникам» в факт: запись `cpu.weight` в idle-cgroup отвергается с EINVAL для **любого** значения. Значит путь in-place resize (`SetPodCgroupConfig`) на idle-поде обречён на ошибку.

Следствия, которые надо заложить сразу:
1. Агент обязан отслеживать изменение `requests.cpu` на живом поде. Если resize случился, пока под в idle, kubelet свою запись не провёл — при снятии idle восстанавливать надо **новый** request, а не тот, что был при входе в idle.
2. В README и в манифестах — явное предупреждение: idle-тир исключать из VPA или держать VPA в recommendation-only. Теперь это подкреплено измерением, а не только чтением кода.
3. Отдельный вопрос — надо ли агенту активно чинить под, у которого resize упал в EINVAL. Пока не решаем: сначала нужно воспроизвести реальный путь `SetPodCgroupConfig`, прямой записи для этого недостаточно.

## Наблюдаемость

Каждое восстановление веса — событие на поде и счётчик с лейблами `node`, `result`. Отдельный счётчик на случай «восстановили, но пересчитанное значение разошлось с кэшем». Без этого молчаливая деградация останется молчаливой.
