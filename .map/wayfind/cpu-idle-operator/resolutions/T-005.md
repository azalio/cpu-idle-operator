# T-005: стендовая проверка lifecycle per-pod cpu.idle

Прогон 2026-08-16 на стенде azalio. Санкция человека и оговорка об авторстве — [T-005.human.md](T-005.human.md).

## Ответ

**Per-pod `cpu.idle=1` переживает всё, что мы проверяли: 60-секундный цикл `qosContainerManager.UpdateCgroups`, событие создания соседнего пода и полный restart kubelet.** Не переживает пересоздание самого пода — это ожидаемо, cgroup новый. EINVAL при записи `cpu.weight` в idle-cgroup **воспроизводится и на pod-cgroup**, а не только на QoS-слайсе. Ветка cgroupfs-драйвера не проверена: на стенде её нет.

## Стенд

| Параметр | Значение |
|---|---|
| Ноды | `cpu-idle-cp` (158.160.1.245), `cpu-idle-worker1` (111.88.145.241) |
| ОС / ядро | Ubuntu 24.04.4 LTS, `6.17.0-061700-generic` |
| Kubernetes | v1.36.3 |
| Runtime | `containerd://2.2.1` |
| cgroup | `cgroup2fs`, чистая v2 |
| Драйвер | `cgroupDriver: systemd` |

Подопытный под: Burstable, `requests.cpu: 500m`, без limits, `cpu.azalio.net/tier: idle`.

## Результаты

### 1. Формула пути подтверждена точно

Вычисленный путь совпал с реальным без единой поправки:

```
/sys/fs/cgroup/kubepods.slice/kubepods-burstable.slice/kubepods-burstable-pod<uid c подчёркиваниями>.slice
```

`cpu.weight` там `20` — ровно то, что kubelet выводит из `requests.cpu: 500m`. Решение из тикета про определение pod-cgroup path (вычислять, а не искать walk'ом) валидно.

### 2. Установка idle меняет вес сама

```
до:     cpu.idle=0  cpu.weight=20
после:  cpu.idle=1  cpu.weight=1
```

Ядро само сбрасывает вес в 1 при переходе в idle. Агенту вес трогать не надо и **нельзя** — см. следующий пункт.

### 3. EINVAL на pod-cgroup — воспроизводится

```python
b'20'  -> errno 22 EINVAL Invalid argument
b'1'   -> errno 22 EINVAL Invalid argument
b'100' -> errno 22 EINVAL Invalid argument
```

Отвергается **любая** запись в `cpu.weight`, включая запись текущего же значения `1`. Это важнее, чем выглядит:

- Формулировка из тикета про prior art («per-pod живёт ниже и коллизию не воспроизводит») **требует уточнения**. Ядерный запрет воспроизводится и здесь. Не воспроизводится другое — *конфликт*: kubelet просто не пишет `cpu.weight` в живой pod-cgroup, поэтому запрет никого не задевает.
- Но любой другой писатель веса на живом поде получит EINVAL. Это ровно путь in-place resize / VPA (`SetPodCgroupConfig`), про который дека предупреждает как про единственную настоящую ловушку. Теперь это не рассуждение, а измерение: **VPA на idle-поде упрётся в EINVAL**.
- Порядок операций для агента жёсткий: сначала `cpu.idle`, потом ничего. Восстановление веса возможно только после `cpu.idle=0`.

### 4. Обратный переход теряет request-derived вес

```
idle 1 -> 0  =>  cpu.weight = 100   (kernel default, не 20)
запись 20 после этого -> OK
```

Подтверждает claim деки дословно. Агент **обязан** восстанавливать вес из `requests.cpu` сам — иначе под, снятый с idle, получит вес 100 вместо 20, то есть в пять раз больше положенной доли. Это молчаливая деградация: ничего не падает, просто под тихо забирает чужой CPU.

### 5. Выживание

| Событие | `cpu.idle` после |
|---|---|
| 8 замеров за 120 с (два полных цикла `UpdateCgroups`) | `1` — ни одного провала |
| Создание соседнего пода на той же ноде | `1` |
| `systemctl restart kubelet` | `1` |
| Пересоздание самого пода | `0`, вес `20` — новый cgroup |

Про соседний под отдельно: вес Burstable-слайса при этом изменился `262 → 270`, то есть kubelet действительно переписал слайс — и per-pod значение это не задело. Это прямое подтверждение тезиса «мы пишем на под, они на слайс, и вот почему это переживает kubelet».

Контраст с Koordinator из чужого замера в деке (BE-слайс держал `idle=1` лишь 66.27% времени, провал каждые ~60 с) объясняется тем же механизмом: слайс переписывается, под — нет.

### 6. SYS_ADMIN не нужен

Под с `privileged: false`, `allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]`, `runAsUser: 0` и hostPath-монтированием `/sys/fs/cgroup` на rw **успешно записал** `cpu.idle` чужого пода. Догадка исследования про `SYS_ADMIN` опровергнута: хватает DAC-прав root на смонтированном hostPath.

Побочное наблюдение по безопасности: это значит, что hostPath `/sys/fs/cgroup` в rw — де-факто право писать cgroup любого пода на ноде. Для DaemonSet это неизбежно, но в манифестах и в README это надо назвать своим именем, а не прятать за «минимальными привилегиями».

### 7. Container-level cgroups

Внутри pod-slice контейнерные scope'ы остались `cpu.idle=0` со своими весами. Idle на pod-cgroup — достаточный уровень: конкуренция с соседними подами идёт именно там.

## Не проверено

1. **cgroupfs-драйвер** — на стенде только systemd. Либо поднимать вторую ноду, либо выносить cgroupfs в out-of-scope (решается в тикете про матрицу supported окружений).
2. **In-place resize / VPA** — EINVAL измерен прямой записью, но не через `SetPodCgroupConfig` на живом поде. Механизм тот же, подтверждения из реального пути нет.
3. **`shouldSetCPUIdle` в libcontainer при `runc update`** — поведение systemd-драйвера при обновлении контейнера не воспроизводили.
4. **Долгая стабильность** — 120 секунд, не часы. Редкий реконсайлер с бо́льшим периодом этим прогоном не пойман.

## Команды для воспроизведения

Под создаётся на воркере с `nodeName: cpu-idle-worker1`, Burstable, `requests.cpu: 500m`, без limits. Дальше на ноде:

```bash
P=/sys/fs/cgroup/kubepods.slice/kubepods-burstable.slice/kubepods-burstable-pod${UID//-/_}.slice
cat $P/cpu.idle $P/cpu.weight            # 0, 20
echo 1 | sudo tee $P/cpu.idle            # -> weight сам станет 1
sudo python3 -c 'open("'$P'/cpu.weight","w").write("20")'   # EINVAL 22
echo 0 | sudo tee $P/cpu.idle            # -> weight станет 100, не 20
```

Namespace `cpu-idle-probe` после прогона удалён.
