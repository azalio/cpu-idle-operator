# T-008: нужен ли control-plane контроллер в v1alpha1

## Решение

**Нет. v1alpha1 — один бинарь, один DaemonSet. Ни Deployment-менеджера, ни leader election, ни CRD, ни webhook.**

Это пересматривает рекомендацию из тикета по reference-архитектуре («два бинаря `cmd/manager` + `cmd/agent`»). Она давалась до того, как решился API-контракт. После решения «голая аннотация, CRD позже» у контроллера не осталось предмета.

## Почему

Контроллер в операторе существует, чтобы реконсайлить объект API-сервера. Переберём, что он мог бы реконсайлить здесь:

| Кандидат на работу контроллера | Есть ли работа |
|---|---|
| CRD-политика → поды | CRD в v1alpha1 нет |
| Валидация аннотации | Гейт прав признан ненужным, webhook отклонён |
| Агрегированный статус по кластеру | Метрики агентов даёт Prometheus, отдельный CR ради этого не нужен |
| Раздача команд агентам | Агент сам смотрит поды своей ноды через informer с `fieldSelector` |
| Уборка за удалёнными подами | cgroup исчезает вместе с подом, финализаторы не нужны |

Ни одной строки. Контроллер в v1alpha1 был бы пустым процессом с leader election и health-probe'ами вокруг нуля работы — и при этом отдельным Deployment, отдельным ServiceAccount, отдельным RBAC, отдельным образом и отдельной поверхностью отказа в README.

## Что это упрощает

- **Kubebuilder не нужен как скаффолд.** Без CRD и webhook от него остаётся только layout. Берём controller-runtime как библиотеку (manager, informer, метрики, healthz, сигналы) без генерации API-типов. `PROJECT`, `config/crd`, `api/` не заводим.
- **Layout сжимается** до `cmd/agent`, `internal/agent`, `internal/cgroup`, `config/`. Каталог `cmd/` сохраняем именно как каталог, чтобы добавление `cmd/manager` в v1beta1 не было переездом.
- **RBAC агента становится крошечным:** `get/list/watch` на pods (ограничено `fieldSelector`), `create/patch` на events. Всё.
- **Leader election не нужен вообще.** DaemonSet по определению один экземпляр на ноду, а ноды не пересекаются по cgroup-дереву. Гонки двух агентов за один файл нет.

## Граница пересмотра

Контроллер появляется ровно тогда, когда появляется CRD-политика с селекторами, то есть в v1beta1. Тогда у него будет настоящая работа: разворачивать селекторы в набор подов и вести статус политики. До этого момента его отсутствие — не упрощение «на время демо», а корректный дизайн для текущего API.

Отдельно: если когда-нибудь понадобится агрегированный вид «сколько подов в idle по кластеру», это сначала пробуем закрыть Prometheus-запросом по метрикам агентов. Заводить CR ради дашборда — плохой размен.
