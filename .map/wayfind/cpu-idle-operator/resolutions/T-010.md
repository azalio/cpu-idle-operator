# T-010: burst-тир через cpu.max.burst

## Решение

**Второй тир в том же операторе.** Ключ тот же, значение другое:

```yaml
metadata:
  annotations:
    cpu.azalio.net/tier: burst      # против  tier: idle
```

Решение человека — [T-010.human.md](T-010.human.md).

Значения взаимоисключающие по построению: аннотация одна, значение одно. Это не ограничение, а точное отражение семантики — `idle` означает «уступаю всё», `burst` означает «беру сверх лимита». Одновременно быть и тем и другим бессмысленно.

## Измерения на стенде

Прогон 2026-08-16, ядро 6.17, `CONFIG_CFS_BANDWIDTH=y`, файл `cpu.max.burst` присутствует на всех non-root cgroup.

| Операция | Результат |
|---|---|
| `burst` при `cpu.max = max` (без квоты) | запись проходит, значение хранится, но неактивно |
| `burst < quota` | OK |
| `burst == quota` | OK |
| `burst > quota` | **EINVAL** |
| понизить `quota` ниже уже выставленного `burst` | **EINVAL на записи `cpu.max`** |
| снять квоту (`cpu.max = max`) при выставленном `burst` | OK, `burst` сохраняется неактивным |

### Оговорка о качестве измерения

Первые два прогона дали неверный результат: буферизованная запись через `open().write()` в Python проглатывала ошибку — она возникает на `close()`, а его код возврата никто не проверял. Выглядело как «запись прошла, значение молча не изменилось». Перемер через `os.open`/`os.write` с явной обработкой `close` показал настоящий `EINVAL`.

Практический вывод, который надо унести в код: **любая запись в cgroup-файл должна проверять ошибку именно на `close`, а не только на `write`**. Иначе агент будет считать успешными записи, которые ядро отвергло. В Go это `defer f.Close()` без проверки ошибки — та же ловушка, и её надо явно избежать во всём слое работы с cgroup.

## Структурная симметрия с idle — и что это даёт докладу

Получилась ровно параллельная пара коллизий:

| Тир | Что ставим | С чем конфликтует | Ошибка |
|---|---|---|---|
| idle | `cpu.idle=1` | запись `cpu.weight` | EINVAL |
| burst | `cpu.max.burst=N` | понижение `cpu.max` ниже `N` | EINVAL |

В обоих случаях включение тира **делает соседний knob частично неизменяемым**, и в обоих случаях страдает один и тот же путь — in-place resize / VPA, который единственный пишет в живой pod-cgroup. Это не два разных дефекта, а один механизм: knob накладывает ограничение на диапазон соседнего knob'а, и ядро защищает инвариант отказом.

Для деки это сильнее, чем частный факт про `cpu.idle`. Тезис перестаёт быть «у cpu.idle есть неприятный угол» и становится «расширенные CPU-knob'ы cgroup v2 вводят межпольные инварианты, о которых Kubernetes не знает, потому что kubelet пишет в pod-cgroup ровно один раз».

## Что это значит для дизайна агента

1. **Burst применим только к подам с limits.** Под без `limits.cpu` получает `cpu.max = max`, квоты нет, копить нечего. Запись пройдёт, но эффекта не будет. Поведение: применяем, вешаем на под **событие** с пояснением, что тир неактивен без limit. Молча делать вид, что политика применилась, нельзя — это тот же класс тихой деградации, что и невосстановленный вес.
2. **Величина burst — политика, а не константа.** Дефолт `burst = quota` (можно накопить один полный период) как самое понятное значение; переопределение через флаг агента. Заявлять оптимальность дефолта нельзя, она не измерена.
3. **Порядок операций.** Сначала убедиться в квоте, потом писать burst; при снятии тира — сначала обнулить burst, потом отдавать управление квотой. Иначе понижение лимита извне упрётся в EINVAL.
4. **Реконсиляция.** Та же схема, что для idle: desired из аннотации, actual из файла, расхождение чиним со счётчиком и событием. Дополнительная проверка — `burst <= quota`, потому что квота могла измениться.
5. **VPA-предупреждение расширяется.** Раньше формулировка была «исключить idle-тир из VPA». Теперь — оба тира: понижение лимита VPA на burst-поде вернёт EINVAL так же, как resize на idle-поде.

## Риск для сообщения доклада

Доклад называется «Поды без CPU limits» и весь построен на том, что лимит не нужен. Burst-тир — про поды, у которых лимит **есть**. Если положить оба тира в один репозиторий без объяснения, зритель решит, что мы сами себе противоречим.

Рамка, которая это снимает и уже есть в деке: сначала формализуем Maximum / Yield / Progress, потом выбираем knob. `idle` закрывает Yield, `burst` — смягчает цену Maximum для тех, кому лимит обязателен по регламенту. Это не спор, а две ветки одного дерева решений. В README тиры должны идти именно в этом порядке и с этой рамкой, а не как список фич.

## Что не проверено

- Влияние `cpu.max.burst` на p99 и на throttling — **не измерено вообще**. Никаких claim'ов про эффект до прогона A/B на том же харнессе, что использовался для idle.
- Пишет ли kubelet `cpu.max.burst` где-либо (для idle аналогичный факт проверялся по исходникам). Предполагаем, что нет, но это чтение, а не замер.
- Переживает ли burst рестарт kubelet и цикл `UpdateCgroups` — для idle проверено, для burst нет. Прогнать тем же скриптом.
