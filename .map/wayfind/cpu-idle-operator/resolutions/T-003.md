# T-003: Reference-архитектура operator + privileged DaemonSet

## Рекомендация

Используй **Koordinator** и **node-feature-discovery** как образцы архитектуры: в одном репо два бинаря (`cmd/manager` и `cmd/agent`), раздельные сервис-аккаунты с минимальными RBAC-правами, контроллер общается с API-сервером, агент получает инструкции через подные FinalizerHandler и status.conditions. Поставляй через Kustomize (kubebuilder-default), метрики собирай через controller-runtime, тесты разделяй: unit на fake-fs для cgroup-логики агента, envtest для контроллера, e2e на kind с privileged DaemonSet. CRD версионируй по hub-and-spoke (v1alpha1 → v1beta1 → v1 с конверсион-вебхуком), лидер-электион на контроллере (2+ реплики), graceful shutdown через сигналы ОС.

## Агент: watch API или команды от контроллера

**Рекомендация: гибридный подход — watch API с асинхронным уведомлением.**

- **Node-Feature-Discovery pattern**: nfd-worker НЕ watch подов напрямую. Вместо этого агент пишет NodeFeature CR (содержит сырые данные), контроллер watch'ит NodeFeature, преобразует, пишет в Node.labels.
- **Для cpu-idle**:
  - Агент (pod-to-cgroup enforcer) **не смотрит API** — вместо этого контроллер пишет Pod.spec.cpuIdle (или аннотацию).
  - Агент слушает kubelet-уведомления **через local cache** (DRA — Dynamic Resource Allocation) или **получает инструкции через ConfigMap вежливого**.
  - Более простой подход: агент watch'ит *только* подов на своей ноде (fieldSelector `spec.nodeName=NODE_NAME`), минимизирует нагрузку на API-сервер.

**Плюсы watch-на-ноде:**
- 1000 нод × 100 подов на ноду = 100k подов, но каждый агент watch'ит только ~100.
- Проще отладить: agent логирует что видит на своей ноде.
- Естественное failover: если agent падает, контроллер видит pod.status неактуальным и пересоздаёт.

**Минусы:**
- API-сервер всё равно хит'ует watch-события от всех agent'ов, но это линейно масштабируется.

**Как в Koordinator**: koordlet (DaemonSet) watch'ит подов на своей ноде через informer с fieldSelector, получает события в реальном времени, пишет статус в NodeMetric CR (агент → контроллер).

### Agent (DaemonSet на ноде)

```yaml

kind: ClusterRole
metadata:
  name: agent-role
rules:
# Читать подов на ноде (fieldSelector spec.nodeName=NODE_NAME)
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]

# Писать в pod.status.conditions (свой статус)
- apiGroups: [""]
  resources: ["pods/status"]
  verbs: ["patch", "update"]

# Читать Node (информация о ноде)
- apiGroups: [""]
  resources: ["nodes"]
  verbs: ["get"]

# Писать свой статус в CpuIdleAgent CR (если заводим отдельный тип)
- apiGroups: ["cpu.azalio.net"]
  resources: ["cpuidleagents"]
  verbs: ["get", "list", "watch", "create", "update", "patch"]
```

### Почему агенту НЕ нужны cluster-wide write-права

1. **Fieldelector spec.nodeName** ограничивает watch на локальную ноду — API-сервер фильтрует на уровне etcd.
2. **NodeRestriction Authorizer** (kubelet по умолчанию): kubelet может修改 только node.status.capacity и pod.status на своей ноде, но агент — это не kubelet, он запускается как обычный pod. Этот authorizer *не помогает* pod'ам.
3. **Вместо этого**: агент работает через сервис-аккаунт с явно ограниченным RBAC (только `pods/status.conditions`, не весь pod, не всех подов на кластере).

## Метрики

**Controller-runtime предоставляет бесплатно:**

| Метрика | Описание |
|---------|---------|
| `controller_runtime_reconcile_duration_seconds` | Latency каждого reconcile (histogram) |
| `controller_runtime_reconcile_errors_total` | Счётчик ошибок по контроллёру |
| `controller_queue_depth` | Текущая длина очереди workqueue |
| `controller_queue_longest_running_processor_seconds` | Latency самого долгого item'а в очереди |

**Добавь доменные метрики:**

```go
// internal/util/metrics.go
var (
    // Pod-level
    podEnforcementDurationSeconds = prometheus.NewHistogramVec(
        prometheus.HistogramOpts{
            Name: "cpuidle_pod_enforcement_duration_seconds",
            Help: "Time to enforce CPU idle on a pod",
            Buckets: []float64{0.001, 0.01, 0.1, 0.5, 1.0, 5.0},
        },
        []string{"node", "pod_namespace", "pod_name", "result"},
    )
    
    // Node-level
    nodeAgentStatus = prometheus.NewGaugeVec(
        prometheus.GaugeOpts{
            Name: "cpuidle_agent_status",
            Help: "Agent status: 1=ready, 0=error",
        },
        []string{"node"},
    )
)
```

**Правила именования (Prometheus style):**
- Метрика для контроллера: `cpuidle_reconcile_*` / `cpuidle_pod_*`
- Метрика для агента: `cpuidle_agent_*` / `cpuidle_enforcement_*`
- Sufix: `_total` (счётчик), `_duration_seconds` (histogram), нет суффикса (gauge).

**Избежать high-cardinality:**
- ❌ Не кладёшь pod_uid, pod_id (каждый новый pod = новая series).
- ✅ Кладёшь `pod_namespace`, `pod_name`, `node` (bounded values).
- ✅ Используй `result="success"|"error"|"timeout"` вместо `error_code="E001"|"E002"|...`.

```go
// +kubebuilder:object:root=true
// +kubebuilder:storageversion  # ← Storage version
type CpuIdle struct { ... }

// Implements hub.Hub для conversion
func (r *CpuIdle) Hub() {}

// api/cpu/v1alpha1/cpuidle_types.go
// +kubebuilder:object:root=true
type CpuIdle struct { ... }

// ConvertTo converts v1alpha1 → hub (v1)
func (src *CpuIdle) ConvertTo(dst runtime.Object) error {
    switch v := dst.(type) {
    case *v1.CpuIdle:
        v.Spec.Enabled = src.Spec.Enabled
        // ... map fields ...
    default:
        return fmt.Errorf("unsupported type")
    }
}
```

```bash
  - name: v1beta1
```

### Graceful Shutdown (Обоих компонентов)

```go
// cmd/agent/main.go (или manager)
sigChan := make(chan os.Signal, 1)
signal.Notify(sigChan, syscall.SIGTERM, syscall.SIGINT)

go func() {
    <-sigChan
    log.Info("Shutdown signal received")
    
    // Агент: откат всех cgroup-изменений перед выходом
    enforcer.RevertAll() // ← Важно: восстанови default cpu.idle = 0
    
    // Контроллер: освободи lease
    mgr.Elected() // ← Контроль-runtime handle'ит это автоматически
    
    mgr.Stop()
}()

mgr.Start(ctx)
```

### Что происходит с pod'ами при смерти агента

**Сценарий:**
1. Pod A запущен на ноде N с `cpu.idle=1`.
2. Agent на N падает (graceful или crash).

**Вариант 1 — Откатить (RECOMMENDED):**
- Agent перед выходом вызывает `echo 0 > /sys/fs/cgroup/.../cpu.idle` для всех pod'ов на ноде.
- Pod A вернётся в режим обычного CPU scheduling.
- **Плюс**: безопасно, pod не висит в broken state.
- **Минус**: потеря cpu-idle оптимизаций.

**Вариант 2 — Оставить как есть:**
- Cgroup-параметры остаются на месте.
- Pod A продолжает работать с cpu.idle=1.
- Новый агент (при рестарте) переприменяет конфиг из CR.
- **Плюс**: непрерывность работы.
- **Минус**: если агент долго не восстановился, может быть расхождение между API и реальностью.

**Выбери Вариант 1** (откат) — это чище, контроллер может переприменить политику при новом старте агента.

**Как реализовать:**

```go
// internal/agent/agent.go
type Agent struct {
    enforcer *Enforcer
    podsCacheОндля reverting
}

func (a *Agent) OnShutdown() {
    // Собери всех pod'ов, что агент когда-то трогал
    for _, pod := range a.podsCache {
        if pod.Spec.CPUIdleEnabled {
            a.enforcer.Revert(pod)  // echo 0 > cgroup
        }
    }
    log.Info("Reverted all pods on shutdown")
}

// В main(), как выше, вызови a.OnShutdown()
```

## Проекты-образцы

| Проект | Компонент | Pattern | Релевантно |
|--------|-----------|---------|-----------|
| **node-feature-discovery** | nfd-worker (DaemonSet) + nfd-master (Deployment) | Pod UID watch на ноде, piping через CR | ✅ Прямой пример: разделение контроллера и агента через CR intermediary |
| **NVIDIA gpu-operator** | Manager + DaemonSet drivers | State machine reconciler, templated manifests | ✅ State-based reconciliation, DaemonSet управление |
| **Koordinator** | koord-manager + koordlet (DaemonSet) | Informer fieldSelector, NodeMetric CR | ✅ Efficient watch-on-node, no cluster-wide gossip |
| **kube-state-metrics** | Single Deployment (не agent) | Prometheus metrics export | ✅ Metrics patterns (не agent-specific, но applicable) |

## Открытые вопросы

1. **Cgroup v1 vs v2 поддержка**: в какой version начинаешь, v1 или v2-only? V2 проще API (cpu.idle уже есть в ядре), но поддержка старше ещё на RHEL 7. Вывод: _v2-first, fallback на v1 если нужно_.

2. **Pod uid → cgroup mount**: как точно отобразить pod UID в директорию cgroup? Kubelet использует podUID в пути: `/kubepods.slice/kubepods-burstable.slice/kubepods-burstable-podXXX.slice`. Достаточно читать pod.status.containerStatuses[].containerID? _Да, или read `/proc/pid/cgroup`_.

3. **Webhook validation**: нужна ли mutation webhook, чтобы автоматически добавить defaults? Или пустить всё в контроллер? _Webhook для ранней feedback, контроллер для defaults — оба помогают_.

4. **Monitoring самого оператора**: как автоматически scraipe Prometheus-метрики оператора в prod? Kustomize добавляет ServiceMonitor CRD или просто Service? _Добавь PodMonitor в config/prometheus/, если у них уже есть Prometheus Operator_.

## Правки после ревью (обязательны к учёту)

Layout, разделение RBAC, набор образцов и разбивка тестов принимаются. Ниже — то, что берём в обратную сторону.

1. **Откат `cpu.idle` при выходе агента — отклонён.** Рекомендация «Вариант 1: `RevertAll()` перед выходом» опасна именно в нашей задаче: rolling update DaemonSet'а (обычное обновление образа) снял бы idle со всех фоновых подов на ноде и вернул им конкуренцию с foreground. Это ломает p99 latency прода во время планового апгрейда — ровно то, от чего оператор защищает. Правильная модель: cgroup-состояние — это **desired state**, а не сессия агента. По умолчанию берём Вариант 2 (оставить как есть, реконсайлить при старте). Отдельный вопрос — надо ли вообще предусматривать явный откат и по какому сигналу; вынесен в тикет.
2. **Совет по метрикам противоречит сам себе.** `pod_name` объявлен «bounded value», хотя у Deployment-подов это `<rs-hash>-<random>` и меняется при каждом рестарте — классический cardinality-взрыв, ровно тот же класс, что и запрещённый там же `pod_uid`. Наши правила: лейблы только `node`, `namespace`, `qos_class`, `result`; идентификация конкретного пода — через логи и events, не через метрики.
3. **«Агент слушает kubelet-уведомления через local cache (DRA — Dynamic Resource Allocation)»** — фактически неверно, DRA к этому отношения не имеет. Рабочий вариант единственный и он же назван дальше: informer с `fieldSelector spec.nodeName=$NODE_NAME`.
4. **Hub-and-spoke conversion webhooks с первого дня — избыточно.** Стартуем с одной версии `v1alpha1`, без conversion webhook. Схема из исследования пригодится на переходе `v1alpha1 → v1beta1`, не раньше; сейчас это лишний webhook-сервер, лишние сертификаты и лишняя поверхность отказа.
5. **Код-примеры иллюстративны, не эталон.** `mgr.Stop()` в controller-runtime нет (остановка через отмену context), `mgr.Elected()` использован не по назначению, в тексте есть повреждённые фрагменты (`podsCacheОндля`, `может修改`). Копировать нельзя, брать только структуру.
6. **Ключ аннотации в e2e-примере не тот.** Там `cpu-idle.azalio.net/enabled: "true"`, решение — `cpu.azalio.net/tier: idle`. Один ключ по всему репо и по обеим декам.
7. **Открытый вопрос №2 (pod UID → cgroup path) уже закрыт** тикетом T-002; ответ там точнее — вычисление через `opencontainers/cgroups`, не чтение `/proc/pid/cgroup`.
8. **Открытый вопрос №1 (v1 vs v2) закрыт:** v2-only, fallback на v1 невозможен — в cgroup v1 нет `cpu.idle`.
9. **`extraMounts` для `/sys/fs/cgroup` в kind-конфиге — под вопросом**, у kind-нод своя cgroup-ветка. Проверять на стенде (T-005), не принимать на веру.
