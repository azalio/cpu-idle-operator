# T-001: Prior art

## Ответ

Существует две реализации: Koordinator пишет `cpu.idle` на QoS-slice (top-level BE), upstream Kubernetes (KEP #5904 / PR #136458) — тоже на slice, но с нерешённой коллизией EINVAL на systemd-driver. Per-pod подход живёт ниже kubelet reconciliation, не перетирается, и избегает обеих проблем.

---

## Koordinator

### Что пишет и где

Koordlet DaemonSet пишет `cpu.idle=1` на уровне **QoS-slice** (`kubepods-besteffort.slice`), не на pod-cgroup. По документации Koordinator, это часть CPU QoS feature, где `schedIdle: 1` в Koordinator CRD транслируется в `cpu.idle=1`.

### Компонент

**Koordlet** — node-local daemon, пишет напрямую в `/sys/fs/cgroup` через resource updater, минуя kubelet. Координирует QoS Manager и набор плагинов; пишет `cpu.idle`, `cpu.weight`, `cpu.max` как часть иерархического управления cgroup.

### Уровень в иерархии

```
/sys/fs/cgroup/kubepods.slice/
  ├─ kubepods-besteffort.slice/cpu.idle = 1  ← Koordinator пишет сюда
  ├─ kubepods-burstable.slice/
  │   └─ pod-cgroup/cpu.idle = 0 (по умолчанию)
  └─ Guaranteed-поды (прямо в kubepods.slice)
```

### Reconciliation

Koordlet пишет один раз и удерживает значение; kubelet не пересоздаёт slice. **Не проверено из кода**: периодический reconсily на slice-уровне или только на создание.

### Статус (по стенду в talk-outline.md)

- Стенд 02.08.2026: Koordinator v1.8, BE-slice `cpu.idle=1` **66.27%** времени; каждые ~60 s провал к `idle=0` на ~20 s.
- 3×5 серия latency с BE-stressor: none 131.61 ms (0/5), Koordinator 103.40 ms (0/5), per-pod агент 44.72 ms (4/5).
- Каузальный гейт — FAIL (нестабильность duty).

## Upstream (issue #136025 / KEP #5904 / PR #136458)

### Scope коллизии

Top-level BestEffort **slice**, не pod-cgroup. Kubelet инициализирует `kubepods-besteffort.slice` с `cpu.weight=1` (или `cpu.shares=2` в v1). Если внешний агент уже установил `cpu.idle=1`, то при запуске kubelet пытается перезаписать weight → kernel возвращает **EINVAL**.

### Статус (проверено 02.08.2026 + перепроверить за неделю доклада)

- **Issue #136025** — open, `kind/feature`, `sig/node`, `triage/accepted`.
- **enhancements#5889** / **KEP #5904** — PR не смержен; документ не live.
- **PR #136458** (`CPUIdleForBestEffortQoS`) — open, без milestone, `needs-rebase`, `priority/backlog`.
- **Статус Beta 1.36** (упоминается в tracking issue) — не означает, что функция смержена; всё ещё в queue.

### Предлагаемый дизайн (из PR #136458)

Писать `cpu.idle=1` на `kubepods-besteffort.slice` внутри `qosContainerManager.UpdateCgroups()`. Файлы:
- `pkg/kubelet/cm/qos_container_manager_linux.go` — основная логика
- `pkg/features/kube_features.go` — feature gate

**Detection-based подход**: не форсировать, если ядро/systemd не поддерживает. Комментарий рецензента: "Perhaps not setting any value if detected will work best" → пропустить запись, если уже установлено.

### Нерешённое

Коллизия EINVAL с systemd cgroup driver (см. ниже); не закрыто в самом PR.

## Ядерные ограничения и коллизии

### Ограничение на ядро

- `cpu.idle` появилась в Linux **5.10** (Alibaba) / **5.15** (upstream SCHED_IDLE, коммит `304000390f88`); kernel.org docs подтверждают 5.15+.
- **Non-root cgroup only**: `cpu.idle` не существует на root cgroup.

### Коллизия EINVAL

Когда `cpu.idle=1` уже установлен на cgroup, попытка записать `cpu.weight` (или `cpu.shares` в v1) вызывает EINVAL. Это происходит в `sched_group_set_shares()` → check `tg_is_idle()` → reject если idle и новый weight ≠ 0.

**Где воспроизводится:**
- kubelet запуск при pre-configured slice с `cpu.idle=1` (issue #136025).
- `runc update` с systemd driver (opencontainers/runc #4143).

### Поведение systemd cgroup driver

**libcontainer `systemd/v2.go`, `shouldSetCPUIdle()` (по комментарию из PR #4143):**
- Если `cpu.idle=1` уже установлен, **пропустить** запись `cpu.weight`.
- Если systemd ≥252: может установить `CPUWeight=idle`; systemd translate → `cpu.idle=1` + `cpu.weight=0`.
- Если systemd <252 или fs2 driver: нет встроенной поддержки idle → нужно handle вручную или error.

**Тихое сброс в 0**: Systemd driver может вывести `cpu.idle` из `CPUWeight` и тихо вернуть `cpu.idle=0` при отсутствии idle-поддержки, что приводит к потере политики.

## Что это значит для нас (per-pod агент)

1. **Иерархия:** Писать на pod-cgroup (ниже QoS-slice) → kubelet не перетирает, koordlet не конкурирует.

2. **Избежать EINVAL:** Pod-cgroup не переписывается kubelet (создаётся один раз в `EnsureExists`), поэтому нет race на `cpu.weight` при `cpu.idle=1`.

3. **Не зависеть от коллизии slice:** Коллизия #136025 касается только top-level BE slice. Per-pod живёт ниже и не воспроизводит её.

4. **Reconciliation:** Per-pod требует периодического обновления (в коде `podtier-agent.py` — loop 2 s), потому что resize-операции могут сбить values. Slice-уровневый подход требует reconciliation на 60 s (Koordinator) или однократной инициализации (kubelet).

5. **Systemd driver:** Оба подхода (slice и pod) работают с systemd v2 на 5.15+. libcontainer уже обрабатывает skip-write при idle=1 (runc #4143).

## Правки после ревью

1. **Битая ссылка:** KEP-tracking указан как `github.com/kubernetes/kubernetes/issues/5889`, а должен вести в `kubernetes/enhancements`. Перед сценой и перед публикацией репо ссылку перепроверить.
2. **Внутреннее противоречие:** в разделе Koordinator reconciliation помечена как «не проверено из кода», в открытых вопросах — как «проверено из кода: нет». Считаем непроверенным. При этом стендовый факт про duty 66.27% с провалами каждые ~60 s — измерение, оно сильнее чтения кода и само по себе указывает на конкуренцию с `qosContainerManager.UpdateCgroups` (тот же период 60 s).
3. **Не подтверждено:** утверждение, что Koordinator пишет `cpu.idle` ТОЛЬКО на QoS-slice. Взято из документации, не из кода koordlet. Если у Koordinator есть и pod-level путь — наш дифференциатор «мы пишем на под, они на слайс» ослабевает, а это тезис отдельного слайда в KubeCon-деке. Проверить по коду до публикации.
4. **`cpu.idle` в 5.10 у Alibaba** — непроверяемое утверждение из вторичного источника. В заявляемой supported-матрице опираться только на upstream 5.15+.
